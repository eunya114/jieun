# planner-comments — 기획자용 한국어 주석

화면 코드를 읽지 못하는 기획자도 "이 화면이 무엇을 하고, 어떤 규칙을 따르고, 문서와 어디가 다른지" 알 수 있게 주석을 단다. 주석은 기획자와 개발자가 같은 문서(PRD, DOMAIN)를 보고 이야기할 수 있게 해 주는 연결고리라서, 정확하고 문서와 같은 말로 쓰는 것이 가장 중요하다.

## 작업 순서

### 1. 대상 파일 정하기
- 사용자가 파일을 말했으면 그 파일만 한다.
- 말하지 않았으면 화면(페이지) 파일 목록을 찾아 보여 주고 고르게 한다. 마음대로 전부 하지 않는다.

### 2. 근거 문서 읽기
- `docs/PRD.md`: 화면별 요구사항(4절), 유저 스토리(US1~US4), 화면 이동(7절), 비즈니스 규칙(5절)
- `docs/DOMAIN.md`: 용어집(1절), 비즈니스 규칙(4절), 데이터 모델(5절)
- 두 문서가 다르면 PRD가 우선이다.

### 3. 원본 보관
- 파일을 고치기 전에 원본을 스크래치패드(임시 폴더)에 복사해 둔다. 마지막에 "주석만 바뀌었는지" 비교할 때 쓴다.

### 4. 파일마다 초안 보여 주고 확인받기
- 파일 하나씩, 어느 줄에 어떤 주석을 달지 초안을 대화창에 보여 준다.
- 사용자가 좋다고 하면 그 파일을 고친다. 고쳐 달라고 하면 반영해서 다시 보여 준다.
- 확인 없이 다음 파일로 넘어가지 않는다.

### 5. 주석 달기 (아래 "주석 형식" 참고)

### 6. 요약 문서 쓰기
- `docs/comments-report.md`를 만들거나 갱신한다 (아래 "요약 문서 형식" 참고).

### 7. 점검하고 보고하기 (아래 "끝났는지 확인" 참고)

## 주석 형식

### 위치
- **파일 맨 위**: 화면 요약 1개
- **주요 부분에만**: 화면 영역(목록, 카드, 하단 버튼 등), 비즈니스 규칙(추천, 1GB당 금액, 변경 제한 등), 상태 처리(불러오는 중, 실패 등), 화면 이동
- 한 줄마다 달지 않는다. 기획자가 궁금해할 "왜/무엇"이 있는 곳에만 단다. 너무 많으면 오히려 중요한 주석이 묻힌다.

### 파일 맨 위 화면 요약
파일 언어의 주석 문법을 쓴다 (JS/TS는 `/** */`, JSX 안은 `{/* */}`, HTML은 `<!-- -->` 등).

```
/**
 * [화면] 요금제 목록
 * 목적: 고객이 현재 요금제와 판매 요금제를 비교하고 바꿀 요금제를 고르는 화면이에요.
 * 관련 유저 스토리: US1, US2, US3
 * 화면 상태: 불러오는 중 / 정상 / 변경 제한 중 / 불러오기 실패
 * 들어오는 곳: 데이터 부족 알림, 변경 완료 화면의 '홈으로 이동'
 * 나가는 곳: 카드 또는 '요금제 보기' → 요금제 상세
 */
```

### 주요 부분 주석 예시
```
// 추천 태그: 최근 3개월 평균 사용량에 맞는 요금제 1개에만 붙여요. (DOMAIN 4-1)
// 1GB당 금액: 월 요금 ÷ 데이터 GB, 10원 단위 반올림해요. 무제한은 '무제한'으로 보여 줘요. (DOMAIN 4-2)
```
- 근거가 있으면 끝에 `(PRD 4-1)`, `(DOMAIN 4-2)`처럼 문서 위치를 적는다. 기획자가 바로 찾아볼 수 있다.

### 문서와 다를 때
- 코드는 고치지 않는다. 주석을 `[확인 필요]`로 시작해 무엇이 다른지 쓴다.
```
// [확인 필요] PRD는 10원 단위 반올림인데, 코드는 버림으로 계산해요. (DOMAIN 4-2)
```
- 문서에 없는 동작도 `[확인 필요]`로 표시한다 (예: 문서에 없는 버튼, 정해지지 않은 열린 질문에 기대는 동작).

## 꼭 지킬 것

1. **주석만 추가하고 코드는 그대로 둔다.** 줄바꿈·들여쓰기·문구 오타도 건드리지 않는다. 주석 때문에 동작이 바뀌면 기획자와 개발자 모두 믿을 수 없게 된다. 고칠 게 보이면 `[확인 필요]`로 남긴다.
2. **쉬운 말로 쓴다.** "~해요"체, 짧은 문장. 개발 용어는 풀어 쓴다.
   - state → 화면이 기억하는 값 / props → 위 화면에서 받은 값 / API 호출 → 서버에 요청 / 렌더링 → 화면에 그리기 / 조건부 렌더링 → 조건에 맞을 때만 보여 주기
3. **DOMAIN.md 용어집의 말만 쓴다.** 예: "신청", "구독", "구독 신청" 대신 **"요금제 변경"**(단, PRD의 화면 이름 "변경 신청 확인"은 그대로 쓴다), 그리고 "현재 요금제", "판매 요금제", "사용 중", "1GB당 금액", "변경 제한", "일할 계산". 같은 것을 다른 말로 부르면 기획자가 다른 기능으로 오해한다.
4. **고객 개인정보는 가린 형태로만 쓴다.** 이름·전화번호·이메일 예시가 필요하면 `홍*동`, `010-****-****`, `a***@*****.com` 처럼 가린 형태로만 쓴다. 코드나 예시 데이터(mock)에 실제 값이 있어도 그 값을 주석·요약 문서·대화창에 옮기지 않는다 (회사 규칙: 고객 개인정보를 절대 포함하지 않는다).

## 요약 문서 형식

`docs/comments-report.md`에 아래 형식으로 쓴다. 이미 있으면 이번에 다룬 화면 부분만 갱신한다.

```markdown
# 화면 주석 요약

## 요금제 목록 — `src/pages/PlanList.tsx`
- 목적: …
- 관련 유저 스토리: US1, US2, US3
- 화면 상태: …
- 들어오는 곳 / 나가는 곳: …
- 단 주석: 7개

## [확인 필요] 목록
| # | 화면 | 위치 | 내용 | 근거 |
|---|---|---|---|---|
| 1 | 요금제 목록 | `PlanList.tsx:42` | PRD는 반올림, 코드는 버림 | DOMAIN 4-2 |
```

## 끝났는지 확인

모두 통과해야 끝이다. 하나라도 실패하면 고치고 다시 점검한다.

1. **바뀐 게 주석뿐인지**: 3단계에서 보관한 원본과 비교한다 (`git diff --no-index <원본> <파일>` 또는 `diff`). 지워진 줄이 없고, 추가된 줄이 모두 주석(또는 주석을 위한 빈 줄)이어야 한다.
2. **모든 대상 파일에 화면 요약이 있는지**: 파일마다 맨 위에 `[화면]`, `목적`, `관련 유저 스토리`, `화면 상태`, `들어오는 곳`, `나가는 곳`이 다 있는지 본다.
3. **[확인 필요]가 요약 문서에 다 있는지**: 코드의 `[확인 필요]` 개수와 `docs/comments-report.md` 목록 개수가 같은지 센다.
4. **개인정보·금지 용어가 없는지**: 새로 쓴 주석과 요약 문서에서 가리지 않은 이름·전화번호(`01\d-\d{3,4}-\d{4}`)·이메일(`\S+@\S+`)과 "신청", "구독"을 찾는다. PRD의 화면 이름 "변경 신청 확인"이나 문서 문구를 그대로 인용한 경우만 괜찮고, 그 밖에는 없어야 한다.
5. **코드가 여전히 도는지**: `package.json` 등에 빌드나 검사(lint, typecheck) 명령이 있으면 실행한다. 없으면 "실행할 명령 없음"이라고 보고한다.

## 마무리 보고

대화창에 아래를 알려 준다.
- 파일별 단 주석 수
- `[확인 필요]` 목록 (요약 문서와 같은 내용)
- 점검 1~5 결과 (통과/실패, 실패했다면 무엇을 했는지)
- 요약 문서 링크: `docs/comments-report.md`
